# Checks for 0.7.3, the update fix and the Update button (2026-11-18, worker 8.40)

Built by worker 8.40 (Opus: updates and offline files are a delicate area, ARCHITECTURE section 12 item 9). Brief: the
Training Agent. Rosario's iPhone (iOS 27.2.1, Home Screen app) never showed "New version ready" for 0.7.1 or 0.7.2,
and Settings had no "Sync now", so the phone still ran old files. Force-quit did not help. Scope add during the build
(the Training Agent, Rosario's wish): a first Settings card "Version X" with an Update button. Independent Opus
checker and auditor, read-only, never the builder; each round each first had to find a mistake planted in its own
private copy (the plant passed every test). Pushed on Rosario's typed "push" in chat 8.40 (cdb5653..273bb24); live
version.js and sw.js say 0.7.3 (2026-11-18 16:23).

## The cause
Two causes, both replayed in headless Chrome (see "How the replay works") and read in WebKit's source code:
- **A. The old cache won.** 0.7.0 to 0.7.2 answered every file with `caches.match(request)`, which looks in every
  cache in the order they were made, so the oldest app cache answers first. Normally the new worker's `activate`
  deletes the old cache. But WebKit stores a worker when its install ends; after its storage process restarts (it does
  on an iPhone) it restores that worker straight as the active one (state "activated") **without running activate**.
  The old cache then stayed, and 0.7.0 files were served by the 0.7.2 worker: the page code said 0.7.0, it never saw a
  waiting worker, so no bar. Replay A1: 0.7.0 to 0.7.2 with activate skipped: active worker 0.7.2, page version 0.7.0,
  caches training-0.7.0 and training-0.7.2, no bar.
- **B. A "new" cache with old files.** The install used `cache.addAll(FILES)`, which goes through the HTTP cache.
  GitHub Pages sends `Cache-Control: max-age=600` and sits behind a CDN, so for up to 10 minutes after a push the new
  cache could fill with the old files. Replay B1: with max-age=600 on the server, the 0.7.2 cache held 0.7.0's
  version.js.
- Spec behaviour that also matters: a waiting worker becomes active when the last page of the app closes (closing the
  app updates without the bar); the browser checks sw.js itself with no HTTP cache by default.

## What was built (app/sw.js, app/js/updater.js, ui/update.js, ui/settings.js; ARCHITECTURE section 7)
- Worker: answers only from `training-<APP_VERSION>`; install fetches each file with `?v=<version>` and
  `cache: "reload"`, `js/version.js` first as a gate (it must say this version), 3 tries per file, 6 at a time; a 404,
  500 or redirect fails the install; a failed install deletes only a cache it made; a completion mark is written last;
  old caches (only `training-*` older than this version, compared as numbers) go in activate and on the first fetch,
  only when the mark is there; offline, a file missing from the own cache comes from the newest older app cache; a
  non-navigation `cache: "no-store"` request goes to the network (the Update button's check).
- Page: registers with `updateViaCache: "none"`; checks at start, and on front and pageshow at most every 15 minutes;
  follows a worker that installs or waits; shows the bar whenever a worker waits; redraws only where `mayRedraw`
  allows (never a workout, the Plan, a sheet, the scanner or typing) and keeps the scroll position; never reloads
  without a tap.
- Settings first card: "Version 0.7.3" and Update (off during a workout). The tap reads the live `js/version.js` with
  no-store: same or older says "You have the newest version."; no signal says "No signal. Try again later." and
  changes nothing; newer runs `reg.update()`, waits for a ready worker (20 s, up to 90 s while one downloads), sends
  SKIP_WAITING and reloads once; no worker in time: deletes the `training-*` caches, unregisters, reloads from the
  network. localStorage is never touched.

## How the replay works
- A small Python server on 127.0.0.1:8017 serves `repro/<name>/app`, where `<name>` is read from a file `current`, so
  the "website" can switch between app copies (0.7.0, 0.7.2, 0.7.3, a test 0.7.4) at any moment. The
  `Cache-Control` header comes from a file `cc` (for example `max-age=600`, like GitHub Pages).
- `drive.mjs` starts headless Chrome with `--remote-debugging-port=9871` and a SHORT profile folder in Temp (a long
  Windows path made CacheStorage fail), and drives it over the DevTools protocol with Node 24's built-in WebSocket
  (no npm). It checks the port is free and that it is Chrome, not another browser already on that port.
- Steps: open `http://localhost:8017/?sw=1#/today` with the old copy, put made-up data in localStorage, reload (now
  controlled), switch the server to the new copy, then reload (not navigate to the same address: that is a
  same-document navigation and checks nothing) and read: page version, controller, active/waiting worker, the bar,
  the cache names, and whether Settings has "Sync now".
- "Activate skipped" (WebKit's restore) is copied by an app copy whose sw.js has no activate handler.
- Copy files with a newer modification time than the old ones: Python's 304 answer has one-second precision.
- Results on the final code: A3 (0.7.0 to 0.7.3, activate skipped) page 0.7.3, caches only training-0.7.3; B3 (with
  max-age=600) page 0.7.3; C3 (app closed instead of Update) the next open runs 0.7.3. Button: same version says "You
  have the newest version."; offline says "No signal. Try again later."; 0.7.3 to 0.7.4 with one tap; the fallback
  (no worker comes) reloads from the network after about 20 s with ver 0.7.4. After the round-2 fixes (replayed
  again): same, offline, 0.7.3 to 0.7.4 in one tap (only the training-0.7.4 cache left), a website with version.js
  0.7.4 but sw.js still 0.7.3 says "The website is still updating. Try again in 10 minutes." and changes nothing,
  and the fallback (one file missing on the site) reloads from the network after about 20 s.
- Screenshots of the new Settings card at 375 x 812, light and dark (scratchpad of chat 8.40, not committed).

## Known limits
- The Update button is page code: it helps only after 0.7.3 reached the phone. The first update must be carried by
  the worker fix itself (install fresh, answer from the own cache).
- The button checks the live sw.js just before its fallback; a CDN copy that changes between that check and the new
  install can still leave the app online-only until the next start installs again. Always release sw.js and
  version.js together.
- Right after the button's fallback reload, the first page can still come from the browser's own short-term cache
  (GitHub's max-age=600) and show the old version; the next open runs the new one (seen in the round-2 replay).
- A failing install downloads the app again (about 7.7 MB) at each start and at most every 15 minutes.
- A stale CDN sw.js older than the phone's version can be installed and offered by the bar (about 10 minutes).
- Whether Safari passes the "no-store" mode to the worker is unknown; the `live=` flag covers both cases.
- The live checks have no timeout of their own: on a very slow signal the button stays busy until the phone gives up.
- If Safari evicts the app's own cache, nothing reinstalls by itself and the card says "You have the newest version."
- A cold open after iOS killed the app mid-workout runs a waiting new version.
- Safari is not available on the computer: the replays ran in Chrome, following the steps WebKit's code takes.
