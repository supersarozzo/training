# Dark mode check, 2026-11-18

Who: dark-mode worker (a task chat started by worker 8.35). Why: Rosario said "the light/dark theme doesn't really
work" and named SimpleHost as the app that does it right.

## What SimpleHost does (read only, `C:\Users\Rosario\dyad-apps\simple-host-v58`)

- `index.html`: `apple-mobile-web-app-status-bar-style` is **default** (iOS draws its own top strip). Never
  `black-translucent`: on iOS 26 it made the home-screen app one strip too short and lost the bottom 47 px.
- iOS 26 **ignores `theme-color`** for the top strip of a home-screen app. The strip takes its colour **from the page
  itself**, and follows a light/dark switch only while **nothing on screen is `position: fixed`** (owner's tests,
  `docs/OLD_DESIGN.md` line 96). `theme-color` is still set on every switch, for other browsers.
- CSS sets the `color-scheme` **property** per theme (`:root { color-scheme: light }`, `.dark { color-scheme: dark }`),
  so the phone's own parts (keyboard, scroll bars, date wheel, form controls) match the app, not the phone.
- The switch is instant: a `theme-switching` class turns off every transition for one frame, so no part fades on its own
  and the page and the top strip change together.
- No web manifest at all, so no fixed colour fights the page.

Cross-checked after the fix against SimpleHost's own answer to worker 8.35 (shared notes,
`simplehost-dark-mode-answer.md`): every cause it lists is covered here. `color-scheme` on the light and both dark
selectors; no-fade switch (two frames); `html` has the canvas background (`app.css`, `html { background }`); the look
is set before the first paint by `boot.js` (an external script, so the CSP needs no hash); the dark rules are guarded by
`:not([data-theme="light"])` (tested); both media `theme-color` tags are rewritten from JS for a fixed choice; no
literal colours outside the tokens. Its advice to remove and re-add the home-screen icon after meta changes does
**not** apply: the status-bar style is unchanged, and re-adding would delete the phone's data.

## The fix

- `app/css/app.css`: `color-scheme: light` in the light map, `color-scheme: dark` in both dark maps (problem 1);
  `html.theme-switching` turns off transitions for the moment of a switch (problem 7).
- `app/index.html`: two `theme-color` tags, one per phone setting (`media`), and `apple-mobile-web-app-status-bar-style`
  `default` written down with the reason (problems 2 and 6).
- `app/js/theme.js` (new, plain functions, tested in Node): the two bar colours and `applyThemeTo(doc, choice)`, which
  sets `data-theme` and both `theme-color` tags. A forced Look writes its colour into both tags; Auto gives each tag its
  own colour, so the browser follows the phone by itself.
- `app/js/boot.js`: also sets both `theme-color` tags before the first paint (problem 4).
- `app/js/ui/theme.js`: uses `app/js/theme.js`, listens for the phone changing light/dark and applies again (problem 3),
  and switches with no fade.
- `app/js/ui/settings.js`: picking Light/Dark/Auto marks the picked button in place, with no redraw and no jump
  (problem 8).
- `app/manifest.webmanifest`: no `theme_color` (one fixed colour cannot be right in both looks; iOS takes the colour
  from the page). `background_color` stays dark (the app's base look). (problem 5)
- `app/sw.js`: `js/theme.js` added to the offline list.

## Auditor m8 (after the fix)

The phone turning light or dark while the app is open (Look = Auto) applied the look without the no-fade class, so
parts with a transition faded for 160 ms. Now `app/js/ui/theme.js` has one `withoutFade()` helper used by both the
Settings switch and the phone-change handler (test: "the phone turning light or dark (Look = Auto) has no fade either").
Not seen by eye: the preview browser does not fire the phone-change event when its light/dark setting is changed (a
test listener counted 0 events), so only the Settings path was seen working.
